# Limitations — AI-Sentinel

> This file lists known limitations, weaknesses, and gaps honestly.
> AGENTS.md rule 9: "Anything unfinished or weak goes in docs/LIMITATIONS.md."

## 1. Real-World Training Data (CSIC 2010 Dataset)

The Isolation Forest is trained on the standard **CSIC 2010 HTTP Dataset** (~28,000 real-world normal HTTP requests from `data/csic_2010/normalTrafficTraining.txt`) combined with the local target application normal patterns (`normal_traffic.py`).

While this provides authentic HTTP request length, entropy, and parameter distributions, note that CSIC 2010 represents traffic from a specific web application (e-Commerce testbed). Different production environments with distinct API shapes (e.g., GraphQL or large JSON payloads) would benefit from retraining on their respective traffic profiles.

## 2. Ephemeral rate/fail counters (bans are persisted)

Active IP bans are persisted in SQLite and reloaded automatically on server restart.
However, short-term sliding counters (rate over 10s, failed logins over 60s) remain
in-memory inside `engine.py`. They reset if the server restarts.

**Mitigation:** For multi-process or clustered deployments, store sliding window
counters in Redis with TTLs.

## 3. Inspection scope

The engine inspects:
- URL path
- Query-string values and parameter names
- POST request bodies (URL-encoded form, JSON bodies, raw uploads)
- `User-Agent` header
- `Cookie` values
- `Referer` and `Authorization` headers
- `X-Forwarded-Host` and `X-Original-URL`

**Not inspected:** binary file attachments content, and client-side web socket frames.

## 4. Rule set is small

The rule engine has ~20 hand-written regex rules. Production WAFs like
OWASP ModSecurity Core Rule Set (CRS) have 100+ rules with far more
coverage. Our rules cover the most common SQLi, XSS, path traversal,
command injection, and scanner detection patterns only.

## 5. No HTTPS / TLS

The demo runs plain HTTP on localhost. In production a reverse proxy
(nginx, Caddy) would terminate TLS in front.

## 6. Single-threaded Flask dev server

`run.py` uses Flask's built-in development server, which is single-threaded
and not suitable for production traffic. A production deployment would use
gunicorn, waitress, or similar.

## 7. ML latency overhead

The Isolation Forest adds ~4–8 ms per request (vs ~0.03 ms for rules alone).
Acceptable for a demo, but for high-throughput production use, batching or a
faster model (e.g. ONNX-exported) would be needed.

## 8. Evaluation data is self-generated

Both the attack payloads (`evaluate.py: ATTACKS`) and the normal traffic were
written/generated by the same author. This means:
- Rules are optimised for their own test set (optimistic recall).
- A truly independent attack corpus would give lower numbers.
- The 14 "tricky legit" requests are a start but not a substitute for real
  user diversity.

## 9. No authentication on the demo site

The "Demo Shop" login is a plain `hmac.compare_digest` comparison with a
hard-coded username/password. There is no session management, CSRF
protection, or account lockout notification. This is intentional — the demo
exists solely to exercise the WAF, not to be a real e-commerce site.

## 10. X-Forwarded-For intentionally ignored

Behind a reverse proxy, the real client IP is in `X-Forwarded-For`. We
deliberately use `request.remote_addr` only, because `X-Forwarded-For` can
be trivially spoofed by the client. A production setup would configure a
trusted proxy list.
